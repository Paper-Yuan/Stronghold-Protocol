## 0. 一页结论

### 0.1 "已更新 0.2.2"到底是什么

**不是 git 合并**——`v0.2.2` 不是 HEAD 的祖先，git 拓扑没变（HEAD 仍 `975585e1`）。它是**工作区层面的部分移植**：并行会话把 0.2.2 的部分特性按文件搬进来了。全量核对（2186 个跟踪文件逐一 hash 比对）：

| 工作区文件状态 | 数量 | 含义 |
|---|---|---|
| 与 v0.2.2 tag 逐字节一致 | **441** | 其中 **434 个 HEAD 本来就一致**（复制式 fusion 的既有事实）；**只有 7 个是并行会话新搬的**（统计页 6 件套 + 1 个 kit 文件 sntlla） |
| 与 HEAD 一致（未动） | 1673 | 含 103 个 `kits/ops` 旧快照、`Battle.js`/`Match.js`/`protocol.js` 等所有引擎核心 |
| 两者皆非（活跃修改） | 72 | endless mod、统计页接线、排行、packs、mod 上传、打包管线 |

**吸收率（按上游自分叉点改动的 594 个文件计）：162/594 ≈ 27%**。且这 162 个里的大头（106 个 kits/ops + test）是**本来就一致**的陈旧快照，不是"更新"的成果。真正的 0.2.2 特性级吸收是：**统计页（PR #323）、tick 容差测试（R23-TICK）、WE1 模组医疗**等少数几块。

### 0.2 一句话判断

**当前工作区是一个"0.2.1-fusion 引擎 + 0.2.2 点状特性 + endless/mod 扩展"的混合态，不是 0.2.2 基线。** 引擎核心（Battle.js 差 2420 行、Match.js 差 3210 行、protocol.js 差 260 行，合计生产代码 38,714 行差异）完全没动。直接在此基础上合 0.2.3 会同时触发 0.2.2+0.2.3 两层冲突，**上午版计划依然是主路径，但必须先落并行会话的工作**。

### 0.3 与上午版计划的差异（修正点）

| 项 | 上午版计划 | 本研讨修正 |
|---|---|---|
| 前提 | "与并行会话协调后清空工作区" | **并行会话的 0.2.2 部分移植 + endless 工作必须先作为 1–2 个 commit 落库**，否则 162 个吸收文件会在 merge 时被当作"我们的修改"重新冲突 |

## 2. 剩余工作量重估

### 2.1 两条路线的抉择（本研讨的核心建议）

**路线 A：先补完 0.2.2 引擎层，再前进 0.2.3（推荐）**
1. 并行会话工作落 commit（endless/统计/packs 为一个 commit；0.2.2 点状移植并入或单独一个）。
2. **完整合并 v0.2.2**（不是点状搬）：`git merge v0.2.2`，按上午版计划的批 A/B/C + 2a–2g 处理 206 个冲突（112 陈旧 + 89 本地增量 + 5 删改，实测见 §1.3 第 3 条）。重点是把 `Battle.js`/`Match.js`/`protocol.js` 的 0.2.2 引擎与规则修正确实吃进来——这是 0.2.3 规则修正（蕾缪安/死芒/守卫治疗）的**依赖前置**，跳过它会让 0.2.3 的 hunk 对不上位置。
3. 合并 v0.2.2 落库、golden 重生成、测试过后，再 `git merge v0.2.3`。此时 0.2.3 相对已合并基线：**47 个净新文件全是干净 add，8 个已吸收文件单边快进，真正要手工的只剩 0.2.2 时已处理过的热点文件的 0.2.3 增量 hunk**。

**路线 B：跳过 0.2.2 直接合 0.2.3**（上午版计划的原始路径）
- 省一次合并周期，但要同时解 214 个冲突（115 陈旧 + 94 本地 + 5 删改），且并行会话未落库的工作会污染每个判断。

**结论：路线 A 略贵（多一轮 golden 重生成 + 测试），但每一步都可验证、可中止，且避免"0.2.2 引擎没进就打 0.2.3 规则补丁"的语义错误。强烈推荐 A。**

## 4. 给并行会话/用户的三个决策点

1. **0.2.2 点状移植要不要继续扩散？** 建议冻结——在完整 merge v0.2.2 之前，不要再手搬 0.2.2 文件（如 sntlla 那样），否则 merge 时该文件会出现"三方都不同"的真三-way 冲突。
2. **本地语音偏好层何去何从？**（§3 风险 1）建议合并时以上游 `voicePrefs.js` 为底座重接我们的双语语音资产，UI 文案保留本地。
3. **路线 A/B 拍板。** 本研讨推荐 A；若用户要快，B 可行但风险集中在一次性 214 冲突。
