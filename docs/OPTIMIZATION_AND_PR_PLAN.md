# 2+2G 服务器优化适配、UI/交互修复及上游 PR 研讨实施计划

## 1. 任务背景与核心目标

当前生产服务器为 **2核 2GB 内存** 架构（阿里云轻量/ECS），公网出口经由 Cloudflare Tunnel 穿透（`https://game.jyuanblog.cc.cd`）。
近期测试发现：
1. **服务器承载问题**：在线达到 160~180 人时容易出现进程崩溃（Node.js 单线程 Event Loop 阻塞、单核被打满、内存逼近上限或大并发广播卡顿）；系统指标显示 CPU 与总内存未完全跑满，但客户端操作延迟显著增加（买棋、调配黏手，响应滞后 300~500ms），现需放开限制基准并提高告警阈值，同时引入**动态调控（准入熔断限流）**以确保游玩体验清爽。
2. **全量预载自动化**：新进入网页端玩家需自动进行两阶段全量预载，静默无感化缓存全量素材（通过已穿透加速的 CDN/CF 隧道）。
3. **游戏内 6 项关键 UI 与交互问题**：
   - 玩家头像旁聊天气泡显示异常（文本单行过窄、换行过大）；
   - 底部战术聊天框尺寸不协调（PC 端过小、手机端过窄）、滚动受阻、退出房间未清空；
   - 商店栏双端适配（手机端过窄，需自适应调整）；
   - 画质与精细度差异修复（连服精细 vs 手机单机模糊）；
   - 干员朝向选择（FacingWheel）增加二段式段落感（放下一段，调向一段）；
   - 高帧率模式设置修复（允许正常关闭，开锁 120 FPS，关锁 60 FPS）。
4. **上游 PR 研讨与吸收规划**：深度研讨上游 PR（#361, #382, #383, #386, #387, #323, #303, #334, #287），以我方当前 UI 与功能架构为主，全盘评估在 PC 端、手机端及双端连服场景下的动态适配。

## 2. 详细技术方案与分步落地设计

### 第一部分：2+2G 硬件性能调优、防崩熔断与操作延迟优化

#### 2.1.1 根因分析
- **伪“CPU/内存未跑满”现象**：Node.js 采用单线程事件循环（Event Loop）。阿里云后台监控是 2 核平均 CPU，显示 50% 时实际上主 Worker 线程的单核已经 100% 打满。
- **操作黏手（买棋、调配延迟大）**：40 多个房间同时处于高频状态广播阶段时，`m.public` 默认节流仅 100ms（10Hz）。当 160 人在线时，每秒产生数千次 JSON 序列化与广播，抢占了 `g.move`、`g.buy` 等用户操作指令的即时处理通道。
- **160~180 人崩溃点**：内存达到 1.4~1.6GB 触发 Node.js 默认的 `max_old_space_size` 垃圾回收停顿（Stop-The-World），进而导致 WebSocket 心跳超时大批断连或 OOM 退出。

#### 2.1.2 改造实施方案
1. **服务端启动参数优化（PM2）**：
   - 调整 Node.js 垃圾回收参数：增加 `--max-old-space-size=1750`，充分利用 2GB 内存；配置 `--nouse-idle-notification`，避免空闲高频 GC 抖动。
2. **动态调控（准入熔断限流）**：
   - 在 `server/lobby.js` 和 `server/net.js` 建立动态容量基线：
     - **安全线（Green）**：在线人数 < 160 或 Equivalent Load Score (ELS) < 160：正常准入。
     - **预警线（Yellow）**：在线人数 160~190 或 CPU > 80%：允许已预载玩家与老玩家断线重连（`welcome` 携带既有 token），新玩家进入提示服务器拥挤。
     - **红线熔断（Red）**：在线人数 ≥ 200 或 Node 事件循环延迟（Lag）> 120ms：对全新连接实施**准入限制**（HTTP/WS 返回友好排队或分流提示：`"服务器当前对局已满载（200/200），正在保护对局稳定，请稍后进入"`），**绝不踢出或影响正在对局的玩家**，保障在场玩家绝对流畅。
3. **操作清爽不黏手（指令快速通道与广播节流）**：
   - **指令优先通道**：将 `g.buy`、`g.move`、`g.lock`、`g.refresh`、`g.art` 等核心操作直接置于 Event Loop 高优先级调度，立刻确认并回包 `ok`，避免排在批量广播之后。
   - **广播节流微调**：将非战斗/休整阶段的 `DELAYS.PUBLIC_THROTTLE` 从 100ms 调整为 200ms（5Hz），减少 50% 的 JSON 字符串化与网络吞吐，释放单核 CPU 压力 30% 以上。
4. **公告与警告提示阈值放宽**：
   - 在 `server/lobby.js` 中将原先的 `loadScore >= 100`（报警）与 `loadScore >= 135`（红线警报）大幅上调：
     - 警报阈值从 100 提至 160；
     - 极高载荷阈值从 135 提至 200；
     - CPU 告警阈值从 75% 提至 88%；
     - 去除频繁弹出的阻塞式警报，改为状态栏微型指示。

### 第二部分：进入者自动全量预载（Auto Full Preload）

#### 2.2.1 业务诉求
进入网页端后，不再需要玩家手动点击弹窗，自动执行两阶段无感全量预载（先 Core 核心包，完成后自动无缝滑动到 Full 全量包），利用 Cloudflare CDN 加速分流静态流量，彻底解决边玩边下导致的卡顿与掉线。

#### 2.2.2 改造实施方案
1. **预载引擎流水线升级 (`public/js/ui/preloadModal.js`)**：
   - 改造 `checkAutoPreload()`：
     - 检测本地 `CacheStorage`，若尚未缓存 `full`，延时 1.0 秒后自动后台启动下载；
     - **两阶段自动衔接**：Core 阶段完成后，不再停止，自动平滑流转进入 Full 阶段（角色全身立绘、全套 Spine 骨骼、局内音效、全技能贴图）；
     - **自适应网络节流**：在后台预载模式下，并发控制为 3~4 个连接，单文件超时重试；当玩家处于战斗阶段（`m.public.phase === 'COMBAT'`）时自动降为低频，不与 WebSocket 争抢带宽。
2. **状态指示与轻量化提示**：
   - 将原居中阻断弹窗改为标题屏幕与大厅右下角微型胶囊指示条（`⚡ 正在加速预载全量资源 45%`），预载完成后自动切换为 `✓ 全量资源就绪`，并即时上报服务端 `client.bundle = 'web_full'`，享受最高准入权重。

### 第三部分：游戏内 UI、交互与手感问题修复

#### 2.3.1 图一：头像旁聊天气泡异常（文本单行过窄、换行过大）
- **现象定位**：`public/css/screens/game.css` 中 `.ebubble` 的 `clip-path`、`padding` 与 `.team__bubble` 宽度限制导致文本被裁剪，左侧留白挤压，换行时 line-height 与 padding 产生过大缝隙。
- **修复方案**：
  - 重构 `.ebubble--text` 样式：
    - 去除多边形硬裁剪 `clip-path` 或自适应气泡尖角（仅左侧保留小气泡三角指示）；
    - 增加自适应最大宽度 `max-width: 4.5rem`（手机端 `min(70vw, 4.0rem)`）；
    - 设定合理的行高与内边距：`padding: .06rem .14rem`，`line-height: 1.35`，`word-break: break-word`；
    - 修复左侧头像对齐基准，确保发出单行或多行文字时左侧均紧凑对齐、完整清晰显示。

#### 2.3.2 图二：底部聊天框适配与历史清理（PC 过小、手机过窄、滚动受阻、退房清空）
- **现象定位**：
  - `public/js/ui/chatBox.js` 与 `public/css/screens/game.css` 中 `.chat-panel` 在 PC 端仅 3.6rem（显得过小），而在手机端 2.8rem 容易遮挡；
  - `.chat-log` 在非 active 状态下设置了 `overflow-y: hidden` 与 `pointer-events: none`，导致鼠标/手势无法上下滚动翻看历史消息；
  - 退出房间时（`room.closed`、`room.leave`、`quitMatch`），`chatMessages` 状态未全量清空，导致重新进入房间仍看到上局残留。
- **修复方案**：
  - **PC/手机独立响应式**：
    - PC 端（桌面横屏）：`.chat-panel` 展开宽度调整为 `4.8rem`，输入框高度提升至 `.38rem`，文字清晰；
    - 移动端（手机横屏）：定位移至左下侧安全区，高度自适应，键盘弹出时自动抬升；
  - **滚动交互优化**：
    - 移除 `.chat-log` 滚动阻断，启用平滑滚动与滚轮直达；增加独立滚动条样式；
  - **房间退出生命周期清理**：
    - 在 `main.js` 的 `backToLobby()`、`net.on('room.closed')` 以及 `matchChrome.js` 的 `quitMatch()` 中显式分发 `store.set({ chatMessages: [] })`，换房即重置。

#### 2.3.3 图三：商店栏双端适配（PC 端正常，手机端过窄）
- **现象定位**：`public/css/screens/game-shop.css` 中，每张卡片 `.scard` 固定宽度为 `1.56rem`，卡片间距 `.08rem`。在 PC 宽屏下布局协调，但在手机屏幕（尤其是 16:9 或 19.5:9 窄视口）上，受到根元素 `rem` 换算影响，卡片被过度压缩变窄，文字与立绘挤压。
- **修复方案**：
  - 引入针对移动端横屏（`@media (max-width: 900px)`、`@media (pointer: coarse)`）的专属响应式网格规则：
    - 手机端采用弹性比例卡片宽度：`width: clamp(1.4rem, 13vw, 1.75rem)`；
    - 精简手机端卡片内边距与冗余装饰，优先放大干员名字与职业图标展示区域；
    - 保持 PC 端原有大气比例不变，双端独立渲染自适应。

#### 2.3.4 角色精细度差异修复（连服精细 vs 手机单机模糊）
- **现象定位**：`public/js/render/app.js` 中的 DPR 判定机制：
  ```javascript
  const isMobile = ...;
  const QUALITY_RES = isMobile ? { high: 2, medium: 1.5, low: 1 } : { high: 3, medium: 1.5, low: 1 };
  ```
  在连接服务器时部分网络环境或设置采用了更高默认 DPR，而在本地单机/离线跑时，检测到手机环境被强行降级至 `medium: 1.5` 甚至更低，且 `devicePixelRatio` 缩放被截断，导致 2D/3D 画布被拉伸模糊。
- **修复方案**：
  - 解绑单机环境下的无差别降采样限制，统一以用户的「画面质量 (Quality)」设置为准：
    - 高画质下允许手机端使用完整物理 DPR（上限由 2.0 提高到 2.5~3.0，匹配现代 OLED 手机视网膜屏）；
    - 保障单机模式与连服模式使用一致的 `resolution: Math.min(window.devicePixelRatio || 1, maxCap)` 渲染管线，消除画质落差。

#### 2.3.5 干员调向操作增加二段式清爽段落感（FacingWheel）
- **现象定位**：原先拖拽棋子到格子上松手时，若手指稍有滑动，即可能同时完成“落子 + 调向”，导致手机触屏操作时误触率极高，难以精确把握干员面向。
- **修复方案**：
  - 改造 `public/js/ui/facingWheel.js` 与 `public/js/screens/game.js` 的状态流转：
    - **第一段（落子锚定）**：干员拖拽到目标格释放后，**必须先锁定停靠并播放落子音效**，呼出清晰醒目的四向罗盘，此时默认不提交任何面向；
    - **第二段（专属滑动/点选）**：提供两种清爽的操作方式：
      1. 触摸任意方向箭头直接确认（Tap to select）；
      2. 从中心向外滑动的段落手感（设置明确的死区阈值与触觉/音效反馈）；
    - 明确区分“落子动作”与“调向动作”，杜绝滑动连带误触。

#### 2.3.6 高帧率模式设置修复与 60/120 帧上限锁定
- **现象定位**：`public/js/render/app.js` 的 `getTargetFps()` 中：
  ```javascript
  const getTargetFps = () => {
    if (settings.highRefresh === false) return 60;
    ...
    if (mode === 'battle') return 60; // 此处硬编码了战斗锁定60帧，且部分逻辑未即时触发 app.ticker 更新
    ...
    return 0; // 0 代表无上限/跟随屏幕，但缺少 120 帧封顶
  };
  ```
  同时设置面板中开关状态更新后，部分生命周期未正确同步给正在运行的 PIXI Ticker，导致用户点击关闭后依然无法生效。
- **修复方案**：
  - 完善 `settingsStore` 与 `app.ticker` 的双向通信响应：
  - 当「动态高刷新率」**开启**时：休整与备战期精确锁定 **120 FPS**（`app.ticker.maxFPS = 120`），兼顾丝滑与控温；
  - 当「动态高刷新率」**关闭**时：全局严格锁定 **60 FPS**（`app.ticker.maxFPS = 60`），确保节能；
  - 修复设置项在 UI 切换时的持久化生效逻辑，保证开关即时生效。
