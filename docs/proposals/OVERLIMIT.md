## 1. 现状：超限现在有什么

### 1.1 它是什么

| 项 | 事实 | 落点 |
|---|---|---|
| 房间模式 | `solo_infinite`（单人）、`coop_infinite`（同盟 2–4 人） | `shared/infiniteMode.js` `SOLO_INFINITE` / `COOP_INFINITE`、`isInfiniteMode()` |
| 它**不是**难度 | `DIFFICULTIES` 只有四档；大厅把超限作为「特殊难度」虚拟项，选中后建房仍传 `difficulty: ABYSS` | `public/js/screens/lobby.js`、`shared/constants.js` `modeIdFor()` |
| modeId | 归一到 `mode_single_abyss` / `mode_multi_abyss`（**这是超限数值高的真正原因**：它直接借用绝境的 `enemyScale` 表） | `shared/constants.js:47` |
| 战绩隔离 | 独立房间，不进常规统计 | 第 1.5 节 |
| 同盟人数 | Boss 血池 `1 + 0.6×(n−1)`、普通波数量 `1 + 0.15×(n−1)` | `partyBossHpMul` / `partyWaveCountMul` |

> **只读实锤**（`node` 探针，见附录 A）：`makeMatch({mode:'solo_infinite', difficulty:'ABYSS'})` →
> `modeId = mode_single_abyss`、`gd.enemyScale(1) = hp 1.2 / atk 1.1`、`gd.enemyScale(15) = hp 3.5832 / atk 1.9487`。
> 也就是说「R1–R15 用绝境表」这件事，是靠**难度字段**实现的，不是靠下面 F1 那个开关。

### 1.2 一条时间轴（现在的规则形态）

```
R1 ─ R14          常规流程（R14 最终攻势）
R15               隐秘核心
────────────────── 以上与非超限局完全一样 ──────────────────
R16 ─ R19         无限普通轮（不设怪池上限）
R20               Boss 轮（契约三选一 → 打 → 通过后开词条抉择）
R21 ─ R24         无限普通轮
R25               Boss 轮 …
R41 ─ R44         …
R45               Boss 轮 · 双 Boss 两阶段（BOSS_PHASE2_WARN 全屏预警）
R46 ─ …           继续，无终点
```

- **Boss 轮节奏**：`r ≥ 16 && r % 5 === 0` → R20/25/30/…；双 Boss 从 R45 起（`isInfiniteDoubleBossRound`）。
- **词条抉择**：只在「刚通过 Boss 轮的下一回合」开（`wantsTraitDraft`：`round ≥ 16` 且 `round−1` 是 Boss 轮且那只领袖**真的被消灭**）。
  所以决策点实际落在 **R21 / R26 / R31 / R36 / R41 / …**。
- **风险契约**：只在 Boss 轮的 PREP 给（`offerBossContract` → R20/25/30/… 的休整期）。
- **一个 5 回合段的形状**：`PREP(契约) → Boss 战 → 词条抉择 → 4 个普通轮`。两个决策点，中间四个普通轮**没有任何决策**。

## 2. 审计发现（八条，都可复现）

> 这八条是「读清楚现状」的产物，**不是新玩法**。F1/F2/F3 属于缺陷面，F4/F5/F8 属于设计面，F6/F7 属于卫生面。

### F1（重要）`gd.overlimit` 是一个**从未被置位**的开关 —— 三处分支是死代码

- 证据：`server/match/gamedata.js:234` 只有 `this.overlimit = false;`；全仓 `rg 'overlimit\s*=\s*true|opts\.overlimit'`
  在服务端只命中 `flags: { overlimit: true }`（战斗 spec），**没有一处**给 `gd.overlimit` 赋真值；
  `Match.js` 建 `GameData` 时传的是 `{ erosion, annMods, contentRules }`。
- 探针（附录 A）：真实超限局里 `gd.overlimit === false`。
- 后果（三处死分支）：
  1. `baseEnemyScale()` 的「超限改查绝境表」（`gamedata.js:1194`）**不执行**——它现在靠 `difficulty: ABYSS` 碰巧达到了同样效果；
  2. `enemyScale()` 的超限 `×1.19^(r−1)` 阶梯（`gamedata.js:1227–1232`）**不执行**——**这一条是好事**，若真生效，
     R60 的 hp 倍率会是 3.5832 × 1.19^59 ≈ **1.0×10⁵ 倍**（实测口径是 33.73 倍）；
  3. `bossLevelTime()` 的超限分支（`gamedata.js:1169–1176`，R20 = 120 s、每档 +10 s）**不执行** → 见 F2。
- 结论：**开关接上之前，别碰这三段**；接上时必须同时删掉 `×1.19` 那条（否则一接就炸）。

### F2（重要）超限的 Boss 轮**没有倒计时**

- 证据：`gd.bossLevelTime(20)` 返回 `null`（探针），`bossRounds.js:192` 的
  `this.deadline = this.sched.instant || !levelTime ? 0 : onClock(levelTime)` → **deadline = 0**。
- 但加时扣血仍在：`bossOvertimeStartReal = levelTime || bossOvertimeAfterReal` = 150 **真实秒**。
- 玩家观感：Boss 轮顶栏的 7 段数字没有/不走，而 150 秒后 LP 开始每秒 −1。这与 `gamedata.js:1166–1176`
  那段注释自己的意图不符（注释写的是「R20 = 120 s、每档 +10 s」，代码却因为开关没接上永远走不到）。
- 最小修法（不改行为、只接开关）：把 F1 里那条死分支改成**按难度即可判定**（`gd.isInfiniteRoundMode` 或
  `Match` 构造时传 `overlimit: this.isInfinite`），并**只接 3 号分支**，1/2 号分支直接删掉。

### F3 结算页的「通过回合」对超限是错的

- 证据：`results.js:122` `roundCap = gd.endless ? m.round : Math.min(m.round, gd.bossRound)`；
  超限 `gd.bossRound = 14` → `teamRounds = victory ? 14 : 13`。
- 探针：把 `m.round` 设 37、走「战术撤退」路径 → `result.roundsPassed === 14`，而
  `result.overlimit.maxRound === 37`。**同一次结算里两个分数打架**（页面显示「通过回合 14」，档案卡显示「最高回合 37」）。
- 修法：超限沿用无尽湮灭的先例（`gd.endless` 那条）→ `roundCap = m.round`，或结算页在超限局改为读 `overlimit.maxRound`。

### F4（设计面）**普通轮与 Boss 轮的需求差 15–200 倍**，4 个普通轮是空的

- R16–R19 需求 DPS 5.6k–6.9k；R20 立刻 108k（19 倍）、R60 1.198M（200 倍）。
- 也就是说：一个 5 回合段里，**4 个回合几乎不消耗玩家资源、也不给决策**，压力全压在 1 个 Boss 轮上。
- 这不是数值 bug（曲线是有意的），而是**节奏形态**问题：段内没有「小高潮」，也没有「小决策」。
  → 这是 A（深潜）与 §9（取点）两个方案的直接动机。

### F5（设计面）Boss 档位的**排序口径**与玩家真正的压力口径不一致

- `buildInfiniteBossWave` 按「本场第 n 次 Boss 战」取 `bloodPoint`（**静态血点**）升序的第 n 档，
  同一条命令里 `getInfiniteBossHp` 又按回合复利。两个口径不保证同序：
  - **ABYSS 路径**（真实超限房）：R20 108,129 → R25 122,972 → R30 153,503，**单调**，看起来没问题；
  - **HARD 路径**（`tools/infinite-demand.mjs` 的默认口径）：R20 **95,304** → R25 **69,246**，**倒挂**。
  - 档位顺序本身是对的（boss_9 280 万 → boss_8 360 万 → boss_10 380 万），所以差异只能来自
    `bossPoolHp()` 的另外几个因子（人数 / 场地 / 难度系数）而不是 `bloodPoint` —— 也就是说
    **「档位顺序 = 玩家的压力顺序」这件事在代码里没有被保证**，只是当前难度下碰巧成立。
- 为什么现在要管：C（通牒）和 §9（取点）都建立在「后期 Boss 更硬」这条基线上。
- 建议：把档位排序改用 `bossPoolHp(gd, id, 1, r)`（实际池血量），或按 `needDps` 复测后
  把结果写进 `test/match/infinite-curve.test.js` 的断言里，让曲线形状有测试兜着。

### F6（卫生面）`INFINITE_MAX_ROUND = 9999` 无引用

全仓只有定义（`shared/infiniteMode.js` 与 `public/shared/infiniteMode.js` 两份拷贝），**没有任何代码读它**。
要么在回合推进处加断言，要么删掉。

### F7（卫生面）R16+ Boss 轮里，**随从完全不吃数值曲线**

- `bossRounds.js:152` 把 `enemyScale: this.gd.enemyScale(this.round)` 塞进 flags；但官方表只到 R15，
  `gd.enemyScale(20)` 返回 `{hpMul:1, atkMul:1, speedMul:1}`（探针已确认）。
- 该 flags 的唯一消费者是 `server/sim/content/bosses.js` 的 `summonMods()`（领袖中途召唤的子怪）——
  于是 R20 之后，Boss 本体在飞涨、它的召唤子怪却永远停在 1×。
- 修法：`enemyScale` 对 `r > 15` 走 `enemyInfiniteScale` 的口径（不要用那条 `×1.19`）。

> 附：`docs/OVERLIMIT-PROGRESS.md` §1.3 的曲线表是 **2026-10-23 分段前**的旧表（R60 写 49.32），
> 现在的实测是 **33.73**（因为 R31–R50 改成了 ×1.05、R51+ 改成了 ×1.04）。文档该改，代码别动。

### F8（设计面）R60 的「能不能打」在**大盟约之间差 80 倍**

- 供给侧实测（表 1.5）：R60 的木桩 DPS 从维多利亚 **26,643** 到炎 **2,133,860**，**80 倍**；
  而 R60 Boss 的需求是 **1,198,319**。也就是说同一回合里，一档 build 富余 1.8 倍，另一档差 45 倍。
- 这意味着三件事：①「超限的难度」不是一个绝对值，而是**相对你所走的大盟约**而言；
  ②任何新机制给出的 ±2%–20% 加成**不可能也不应该**去填这 80 倍——那是平衡问题（`tools/bond-matrix.mjs` 的活）；
  ③新机制该做的是**让每一段有决策与意义**，不是「让弱 build 也能打到 R60」。
- 另外：R60 的需求（1.198M）刚好卡在「谢拉格 1.12M / 炎 2.13M」之间——**这两个数字碰巧非常接近**，
  说明当前曲线大致是「按强 build 的 1/1.5 设计」的。若要动曲线（F5），以这条为锚。

## 3. 六条硬约束（4 条通用 + 2 条超限专属，任何方案进场前先过）

1. **门**：所有逻辑 gate 在 `m.isInfinite` / `battle.flags.overlimit`；普通模式、湮灭、炸惊的
   `m.public` 与 `m.result` **逐字节不变**，`test/golden/*.json` 零位移。
2. **确定性**：随机一律 `createRng(deriveSeed(m.seed, '<tag>', …))`；不许 `Math.random`、不许时钟。
3. **双端**：每条改动都要问「浏览器里算不算同一份」。现有做法是「服务端算、客户端只渲染」
   （`views.js` 下发），新方案照抄。
4. **i18n**：任何新文案都要 `t('…')` + `public/i18n/{en,ja,ko,zh-TW}.json` 四包 +
   `node tools/i18n.mjs check --all --strict`。**本文不新增任何 `t()` 调用**。

**另外两条超限专属的**：

5. **同盟兼容**：`coop_infinite` 存在。凡是「需要一个人拍板」的机制，v1 一律只对 `solo_infinite` 开放
   （或要求全队同意），否则会在同盟里卡死（现有词条抉择就是「逐人选」的 `trait.order/idx/picks`，可以照抄）。
6. **合成列表的坑**：`Match.js` 末尾的 `for (const part of [...])` 里少放一个 mixin，
   方法就**不存在**，`guard` 会把它吞成 `TypeError` 并让阶段卡死——2026-10-26 已经因为漏了 `MatchTraitDraft`
   出现过「R20 打完永远进不了词条抉择」。**新 mixin 必须同时加进那张表 + 写一条 e2e 断言**。

## 4. 作用域矩阵（先证明「不重复造」）

行 = 机制，列 = 它**改什么**。一个合格的新方案必须在「作用域」这一列占一个空格子。

| 机制 | 出处 | 选择时机 | 作用域 | 改的是 | 可重复次数 |
|---|---|---|---|---|---|
| 炸惊 · 惊变三选一 | `docs/ZHAJING.md` §1.1 | R1（整局一次） | 整局 | 阵容内容（卡 + 羁绊 + 数值） | 1（+ 重抽） |
| 湮灭 · 负面藏品三选一 | `docs/EXTENSION_MODE.md` §3.2 | R1 | 整局 | 规则/经济/战斗域 | 1 |
| 湮灭 · 侵蚀档位 | 大厅建房 | 建房前 | 整局（且是**全局指数**） | 敌人数值曲线 | 0（开局定死） |
| 超限 · 词条抉择 | 本文 §1.3 | 每 Boss 后 | 整局 + 一只怪 | 我方永久 | N（每 5 回合） |
| 超限 · 风险契约 | 本文 §1.3 | Boss 轮 PREP | **一个 Boss 波** | 该波 + 一次性奖励 | N |
| 超限 · Boss 词缀 | 本文 §1.3 | 每 Boss 波 | **一个 Boss 波** | 该波敌方 | N（自动抽） |
| **A 深潜**（§5） | 本提案 | 普通轮 PREP | **回合轴线**（跳 1–2 回合） | 这一波的数值 + 记分 | ≤ 3/局 |
| **B 熔铸**（§6） | 本提案 | 休整期 | **层数 → 永久属性** | 我方永久（花的是**已有**增量） | ≤ 5/局 |
| **C 通牒**（§7） | 本提案 | Boss 通过后 | **永久（敌方）**，可叠加 | 所有未来 Boss | N（每 Boss 一次） |
| **D 每日同调**（§8） | 本提案 | 建房前 | **元层**（种子/榜单） | 起点相同、分数可比 | 每天 1 次 |
| **E 取点**（§9） | 本提案 | 每段段首 | **一段 4 个普通波** | 出怪包 | 5+ 次 |

读法：

- 词条 = 我方的**永久**；通牒 = 敌方的**永久**——两者是一对，不重叠。
- 契约 = 一个 Boss 波；深潜 = 一个普通波 + 回合轴——两者不重叠。
- 取点 = 一段 4 个普通波——**比契约大、比词条小**，是唯一一个「段」级作用域，因为只有超限有「段」。
- 熔铸 = 花掉**已有的**层数；没有任何既有机制消耗层数（层数只增不减，除了「离散」词条的随机 −10 层）。

## 5. 方案 A · 深潜（DIVE）

> 一句话：**用「少打一轮」换「打一轮更狠的」**——把 4 个空转的普通轮压缩掉一段，代价是收入与层数收入。

### 5.1 核心循环

```
普通轮 PREP（R16 起、非 Boss 轮）
   ├─ 玩家看到：顶栏胶囊「DIVE 1 · 本段还剩 1 次」
   ├─ 点开 → 「深潜 1 层 / 深潜 2 层 / 取消」
   ├─ 选 1 层：本回合的波次按 (r+1) 的数值生成（不出 Boss），时限不变
   ├─ 通过（不漏怪）→ 直接推进到 r+2（跳过 r+1 这一轮），并保留记分
   └─ 失败（漏怪扣 LP 到 0）→ 照常结束，本局终止

约束：
   · 每 5 回合段最多 1 次，每局最多 3 次
   · 数值回合封顶在「下一 Boss 回合 − 1」（R18 深潜 2 层 → 用 R19 的数值，不越到 Boss 轮）
   · 被跳过的回合：不结算收入（12 资金/回合）、不结算完美作战、不结算层数收入
```

### 5.2 为什么只能属于超限

| 对照 | 为什么不能照搬 |
|---|---|
| 炸惊三选一 | 它是 **R1 一次、整局**的阵容选择，与「回合轴」无关。炸惊只有 14 回合，跳一轮等于跳掉 1/14 的流程，没有腾挪空间；超限的回合数是无穷的，**跳过一轮才有意义**。 |
| 湮灭藏品 + 侵蚀 | 侵蚀是**建房前定死**的全局指数（1–6 档），玩家在局内不能改「自己走多快」；深潜改的正是**局内速度**。 |
| 既有词条/契约/词缀 | 三者的作用域都是「永久」「一个 Boss 波」「一个 Boss 波」，**没有一个是回合轴**。 |
| 结构上的唯一性 | 只有超限有「单调、无上界的回合曲线」：`hp ×1.06`/回合是**纯 r 的函数**，所以「用 r+N 的数值打一波」是良定义且可解释的。14 回合的模式里这个操作没有对象。 |

### 5.3 可量化的难度曲线

以 R16 的实测基线（21 只 / 67.2 万 HP / 时限 120 / 需求 DPS 5,602 / 需求 HPS 10,447）为例，
下一 Boss 轮是 R20，所以数值回合上限是 **R19**（不会越到 Boss 轮）：

| 选择 | 该波数值回合 | hp 倍率 | atk 倍率 | 需求 DPS | 需求 HPS | 收入代价 | 记分 |
|---|---|---|---|---|---|---|---|
| 不深潜 | R16 | ×1.0000 | ×1.0000 | 5,602 | 10,447 | — | — |
| 深潜 1 层 | R17 | ×1.0600 | ×1.0301 | **5,938** | 10,762 | −12 资金、−1 次层数收入 | +1 回合 |
| 深潜 2 层 | R18 | ×1.1236 | ×1.0611 | **6,294** | 11,085 | −24 资金、−2 次层数收入 | +2 回合 |

> 只按倍率外推，不重算「种类数 / 每种数量」（那两个数按回合阶梯变，`perKind` 在 R22 才从 3 变到 4，
> 所以 R16–R19 区间内不跳档）。真实值请用 `tools/infinite-demand.mjs` 逐回合复测。

- **为什么每层只贵 6%**：因为 `enemyInfiniteScale` 的 hp 步长就是 1.06。想让「深潜」更痛，**不要**改这条曲线
  （它是全模式的基准），而是**加层数**（1 层 = 1.06，3 层 = 1.19）或**收紧收入补偿**。
- **代价侧的量化**（这才是真正的成本）：
  - 资金：`gd.income(r) = 12`（R10 起恒定）→ 每跳 1 轮少 12 资金 = 6 次商店刷新。
  - 层数：`tools/infinite-teams.mjs` 的模型是「R15 起每回合大/小盟约各 +50 层」→ 每跳 1 轮少 50 层。
    按现有规则折算：萨尔贡 5%/100 层 ⇒ −50 层 ≈ **−2.5% 攻击**；阿戈尔 0.8%/层 ⇒ **−40% 攻击**。
    **跳一轮的代价随你选哪条大盟约而剧烈不同**——这本身就是一次有意义的读牌。
- **记分上界**：每局最多 3 次 × 最多 2 层 = 最多 +6 回合（相对 R40 约 +15%）。若业主不接受任何记分通胀，
  改成「跳过不计分」即可（见 5.5 风险 1）。

## 6. 方案 B · 熔铸（MELT）

> 一句话：**把「层数」从只会涨的数字，变成可以花的货币**。触发点是「哪条盟约的尾巴已经不值钱了」。

### 6.1 核心循环

```
休整期（任意 PREP），打开某条盟约的详情（现成的盟约 popup）
   ├─ 底部多一行：「熔铸 100 层 → 1 熔铸点」，附收益预览
   ├─ 点下去：该盟约 −100 层，熔铸点 +1（第 k 次的价格 = 100 + 50(k−1)）
   └─ 熔铸点在三选一里花：
        ① 全队攻击 +4%（可叠加，无硬上限）
        ② 下一次词条抉择变「4 选 1」
        ③ 本段商店可买 tier +1（多买一档装备）

约束：
   · 只能对**当前层数 ≥ 价格**的盟约熔铸
   · 只在 PREP 可做（层数在战斗中会被 联防 / 结算改写，不在战斗期动它）
   · 每局最多 5 次（1000 层总额）
```

### 6.2 为什么只能属于超限

| 对照 | 为什么不能照搬 |
|---|---|
| 炸惊三选一 | 炸惊的层数上限仍是 **999**（`BOND_LAYER_CAP` 没被改），140 层已经是「一条大盟约的全部家当」，熔铸它会直接把 build 熔没。层数只有在 **9999 上限 + 每回合 +50** 的超限里才是**盈余**。 |
| 湮灭藏品 + 侵蚀 | 湮灭的成长轴是**侵蚀指数**（开局定死），不是层数；它的藏品是「白拿」的一次性强化，没有可消耗的池子。 |
| 既有超限机制 | 词条只加不减、契约只影响一波、词缀是敌方的。**没有任何既有机制消耗层数**——层数在超限里是目前唯一「只进不出」的资源。 |
| 结构上的唯一性 | `INFINITE_BOND_LAYER_CAP = 9999` + 每回合层数收入 ≈ 50 ⇒ 只有在超限里，「某个盟约的边际收益已经掉到 0」这个状态才**可达**（见 6.3 的边际表）。 |

### 6.3 可量化的难度曲线（用现有盟约规则算边际，不发明新表）

熔铸 100 层，对每条大盟约**损失多少**（按 `server/sim/content/bonds/core.js` 的超限分支）：

| 盟约 | 规则 | 100 层的边际价值 | 熔铸是否划算 |
|---|---|---|---|
| 维多利亚 | 锤子 30 件封顶（≈750 层）；之后每 50 层 +1% 伤害 | 750 层以上：**+2%** 伤害 | **划算**（+4% 攻击 > −2%） |
| 萨尔贡 | 每 100 层 +5% 攻击 | **+5%** 攻击 | 略亏（+4% < −5%） |
| 拉特兰 | 每发 4%→8%（累计上限 700%） | 封顶后 **0** | 封顶后极其划算 |
| 阿戈尔 | 每层 +0.8% 攻击 | **−80%** 攻击 | **绝不划算** |
| 炎 | 生命 +15% + 0.2%/层 | **−20%** 生命 | 看生存余量 |
| 叙拉古 | 3%→8% 概率 + 0.5% 目标最大生命 | 中等 | 看命中需求 |

- **曲线形状**：熔铸不改变敌人曲线，它改变**玩家的成长斜率**。k 次熔铸的累计成本 = `100k + 25k(k−1)` 层；
  k=5 时 1000 层 ≈ 20 个回合的全部层数收入（按 +50/回合）⇒ 一轮 R16–R60 最多换到 5 点。
- **压力侧**：5 点全买攻击 = +20% 全队攻击；对照 R20→R60 的敌人 hp 从 4.80× 到 33.73×（×7），
  所以熔铸**不可能**抵消曲线，它只能「把浪费掉的层数捡回来」。这正是我们要的：一个**不破坏曲线**的增益。
- **可读性**：需要熔铸的玩家必须读懂「这条盟约的边际」，而这段文本**已经存在**：
  `public/js/ui/overlimitBondText.js`（公式）+ `overlimitBondNow()`（代入层数）。熔铸弹窗直接复用。

## 7. 方案 C · 通牒（BOSS STAKE）

> 一句话：**每打死一个 Boss，敌方永久加码一条、你也永久变强一点**——把「无限」变成一场军备竞赛。

### 7.1 核心循环

```
通过 Boss 轮（含双 Boss 的两个阶段都打完）
   ├─ 弹出「通牒」：从 2 张里**必须选 1 张**（不能跳过）
   ├─ 每张 = 一条永久敌方词缀 + 一条对称的我方补偿
   ├─ 立即生效，作用于**所有未来 Boss**（不是下一次）
   └─ 选完才进入词条抉择（或合并成同一张「段间」界面，见 §9.3）

第一次通牒（R20 后）起：
   敌方 Boss HP ×(1 + 0.06n)、随从 +floor(n/2)
   我方全队攻击 ×(1 + 0.03n)
   → 净压力 (1.06/1.03)^n ≈ 1.029^n
```

### 7.2 为什么只能属于超限

| 对照 | 为什么不能照搬 |
|---|---|
| 既有 Boss 词缀 | 词缀是**每波抽一条、只影响这一波**（`applyBossAffix` 把结果写进 `wave.affix`）。通牒是**永久叠加、玩家自选、跨波生效**——它需要一个「能活过很多个 Boss」的模式，而那只有超限。 |
| 炸惊三选一 | R1 一次、抽的是**我方阵容**（惊变卡）。通牒是**敌方**的、可重复的。 |
| 湮灭藏品 + 侵蚀 | 湮灭的 Boss 只有「那一对」（14/19 回合内），且它的加码是**开局定死的侵蚀指数**；通牒是**局内逐次加码**，需要「Boss 数量 > 2」才成立（超限的 Boss 池有 8 档，R20–R55 逐个出场）。 |
| 结构上的唯一性 | `buildInfiniteBossWave` 按「第 n 次 Boss 战」取池里第 n 档、**用完后停在最强档**；一旦档位用尽（R55 之后），Boss 只是靠 `getInfiniteBossHp` 的数值长胖，**没有任何新东西**。通牒正好接管「R55 之后」，让后期 Boss 在**机制**上继续变化。 |

### 7.3 可量化的难度曲线

以 R40 Boss 轮（需求 DPS 249,012）为基线，累计 n 条通牒后：

| n | 敌方 HP | 我方攻击 | 净压力 | 需求 DPS（R40 类比） |
|---|---|---|---|---|
| 0 | ×1.000 | ×1.000 | 1.000 | 249,012 |
| 2（R30 后） | ×1.124 | ×1.059 | 1.061 | 264,200 |
| 5（R45 后） | ×1.338 | ×1.159 | 1.155 | 287,600 |
| 8（R60 后） | ×1.594 | ×1.266 | 1.259 | 313,500 |
| 12（R80 后） | ×2.012 | ×1.425 | 1.412 | 351,600 |

- **为什么不是更狠**：真正决定「还能不能打」的是 `hp ×1.06/回合` 的曲线（R40→R60 是 ×2.4）。
  通牒只加 ~1.03×/次，**绝不抢曲线的戏**；它提供的是「每一段 Boss 的手感不一样」，而不是「更陡」。
- **每张通牒的取值区间**（一阶段只用数值/数量，不碰受击钩子——和现有 `bossAffixes.js` 同一手段）：

| 通牒 | 敌方 | 我方 |
|---|---|---|
| 强袭 | Boss HP +6% | 全队攻击 +3% |
| 猛毒 | Boss 随从 +1 只（`tag:'part'`，不计漏怪） | 词条重抽 +1（累加到下一次抉择） |
| 铁壁 | Boss def +8% / res +6 | 装备位 / 商店 tier +1 |
| 疾行 | Boss 及随从 speed +4% | 全队攻速 +5 |

- **二阶段（需要 Boss 受击钩子，建议延后）**：护盾（`addBuff(shield)` per boss）、反伤（Boss `damaged` 钩子）。
  这正是 `handoff/OVERLIMIT-FUN-2026-10-26.md` 已经判过的二阶段内容，**不要**在一阶段混进来。

## 8. 方案 D · 每日同调 + 本机榜（DAILY）

> 一句话：**同一天、同一个种子、同一个起点**——把「我能走多远」变成一个可比的问题。

### 8.1 核心循环

```
大厅「特殊难度」卡（超限那一张）多一行开关：每日同调
   ├─ 打开后建房：seed = dailySeed(本地日期)，其余完全不变
   ├─ 于是同一天的所有局：词条序列、Boss 档位、词缀、深潜/契约的牌面全都一样
   ├─ 结算：档案卡多一页「今日榜（本机）」，列本机最近 5 次
   └─ 不联网、不上报、不影响任何既有统计
```

### 8.2 为什么只能属于超限

- 只有超限的分数是**无上界的回合数**（`m.result.overlimit.maxRound`），同种子才有区分度。
- 官方四档在 R14 结束，`roundsPassed` 恒 14；湮灭无尽在 `gd.endless` 下也不封顶，但它的分数受
  **开局选定的侵蚀档位**支配（同种子不同档位不可比），要做每日榜得先把「档位」也钉死——那是另一件事。
- 炸惊没有回合轴之外的可比量。

### 8.3 可量化的难度曲线

- **0 数值改动**：这条方案不动任何曲线、不新增任何常量，只改种子来源。
- 唯一要定义的是种子的确定性：`seed = deriveSeed(crc32('sp-daily:' + ymd), 'overlimit-daily')`，
  用现成的 `server/sim/rng.js`（`createRng` / `deriveSeed`），**不用 `Math.random`**。
- 榜的度量：`maxRound`（主）、`bossKills.length`（次）、`maxLayers`（展示）。

## 9. 单列 · 镜牢取点（轻量版）

> 参照 Limbus Company 的「镜牢」：每一层打完在几个**节点**里挑一个，节点决定下一层的敌人与奖励。
> **轻量版去掉地图、去掉路径、去掉分叉树**：只有「每段 3 选 1 + 一张节点类型表」。

### 9.1 核心循环

```
每段的段首（R16 / R21 / R26 / R31 / R36 …）
   ├─ 三张节点卡，选 1 张（没有「跳过」）
   ├─ 该节点决定这一段的 4 个普通轮的**出怪包** + 一次性奖励
   └─ 段末的 Boss 轮固定（不受节点影响）

一段 = 4 个普通轮 + 1 个 Boss 轮 = 5 回合
   R16–R20 / R21–R25 / R26–R30 / R31–R35 / R36–R40  ← 前 5 段
   R41 起：段号继续涨，节点表 +1 档（同一张表，tier 提高）
```

### 9.2 节点类型表（5 类，全部落在**已有**的出怪旋钮上）

| 节点 | 出怪包（相对基准） | 生成器旋钮 | 需求变化（估算） | 奖励 |
|---|---|---|---|---|
| **交锋** COMBAT | 基准（6–7 种 × perKind） | 无 | ×1.00 | +2 资金 |
| **猎场** HUNT | 数量 −1/种，精英占比 4:6 → 7:3 | `perKind −1`、精英比例 | HP ×0.8–1.3（取决于抽到谁） | 一件 tier 装备 或 免费刷新 ×2 |
| **军械** ARSENAL | 种类 +1、每种 −1 | `kindCount +1` | 总量 ×1.0（种类多、每种少） | 本段商店可买 tier +1 |
| **异象** ANOMALY | 基准 + 一条敌方修正 | `mods.atkMul ×1.15` 或 `speedMul ×1.10` | HPS/攻速压力 +15% | 词条重抽 +1 |
| **静滞** STASIS | 种类 −1、每种 −1 | `kindCount −1`、`perKind −1` | 总量 ×0.7 | LP +1 或 +4 资金 |

> 数字依据：`data/enemies.json` 的平均白值 —— 普通怪 avg HP 4,197、精英怪 avg HP 94,956（**22.6 倍**），
> 所以「精英占比」是这张表里最狠的旋钮；`perKind = min(6, 3+floor((R−16)/6))` 与
> `kindCount ∈ {6,7}` 是总量旋钮。

### 9.3 与波次、契约、词条的**对齐关系**

| 时点 | 已有决策 | 取点 | 是否撞车 |
|---|---|---|---|
| 段的第 1 个回合（R16/R21/…）PREP | —（R21 之前刚做完词条抉择） | **取点在这里** | 不撞：词条是「上一段 Boss 的结算」，取点是「本段的编排」 |
| 段末 Boss 轮 PREP（R20/25/…） | 风险契约 | — | 不撞：契约只改 Boss 波 |
| Boss 通过的下一回合 | 词条抉择 | — | 不撞：词条是永久 |
| 任意普通轮 | — | — | 取点不改单波，它改一整段 |

**推荐交互**：把「词条抉择 → 通牒 → 取点」串成**同一个段间界面**（三个页签，顺序执行），
这样每 5 回合只有**一次**被打断，而不是三次。

### 9.4 可量化的难度曲线

需求 DPS 的近似式（落地用 `tools/infinite-demand.mjs` 逐段复测）：

```
需求DPS(段) ≈ 基准需求 × (kindCount / 6.5) × (perKind / perKind₀) × 1.06^(数值回合 − 基准回合) × 节点系数
```

以 R26 段为例（scale ≈ 6.81，perKind = 5，kindCount 6–7，30–35 只）：

| 节点 | 相对基准 | 需求 DPS（估算） | 段末 Boss R30（实测 153,503） |
|---|---|---|---|
| 交锋 | ×1.00 | ≈ 17,700 | 153,503 |
| 猎场 | ×0.85–1.10 | ≈ 15,000–19,500 | 同上 |
| 军械 | ×1.00 | ≈ 17,700（种类 +1） | 同上 |
| 异象 | ×1.15（HPS 侧） | ≈ 17,700（DPS 不变） | 同上 |
| 静滞 | ×0.70 | ≈ 12,400 | 同上 |

**读出来的结论（重要）**：即使把 4 个普通轮改成「异象」，普通轮的需求也只在 1.2–2 万，而 Boss 轮是 15 万。
**取点不可能靠数值把普通轮变成高压**——它给的是「节奏与资源的编排」（装备/商店 tier/LP/重抽），
压力仍由 Boss 轮承担。这一点必须在设计稿里写清楚，否则会做出一个「看起来很忙但没难度」的系统。

> 与供给侧对照（F8）：R60 的队伍输出在 2.7 万–213 万之间，而 Boss 需求 120 万。
> 所以「这一段选了什么」真正影响的是**你能否带着正确的资源走进 Boss 轮**，而不是「普通轮会不会打死你」。

## 附录 C · 一句话总结

超限现在**已经有**四层决策（词条 / 契约 / 词缀 / 撤退）和一套完整的 HUD，缺的不是「玩法」而是三样东西：
**① 一个能被玩坏的开关和三处死代码（F1/F2/F3）；② 段内的节奏与决策（普通轮需求只有 Boss 轮的 1/15–1/200）；
③ 无上界回合轴带来的两个空作用域（回合轴、段）**。
本文的五个提案分别填这三个洞，且每一个都能落在现成文件上——**没有一个需要新模式、新难度或新数据集**。
