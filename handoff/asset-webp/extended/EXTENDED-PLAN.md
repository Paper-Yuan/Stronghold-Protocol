## 0. 结论（先看这 7 条）

1. **皮肤立绘是最大的单块蛋糕**：`char/illust/skin/` 实测 **277 张 / 886.04 MiB**，q90 外推 **158.94 MiB**，省 **727.11 MiB（82.1%）**——比精二的 580.29 MiB 还大 25%。
2. **精一 15 张全部实测（无外推）**：63.59 MiB → **9.90 MiB（6.42×，省 84.4%）**。但两组必须分开看：
   - **小图组 `_1`（5 张 / 2.63 MiB）**：转 q90 后只有 **0.42 MiB**，看起来 6.26× 很漂亮，**但绝对收益只有 2.21 MiB**，占全案 0.15%。分组的真正意义是——**它们的体积本来就不值得单独排期**。
   - **大图组 `_2` + `_skin1`（10 张 / 60.95 MiB）**：→ **9.48 MiB（6.43×，省 84.4%）**，绝对收益 51.47 MiB，**这才是精一里值得做的事**。
3. **`exact=False` 的收益被严重低估了**：E1 报的 2.3%–8.2% 只适用于常规立绘。精一 `_1` 组有 **81.5%–84.9% 全透明像素**，`exact=True` 白白保存了这些像素底下的 RGB——改成 `exact=False` 直接 **再省 48.1%**（0.81 → 0.42 MiB）。收益大小和全透明占比强相关：透明 82–85% → 省 48%，透明 35–46% → 省 14%，皮肤（透明 26–78%）→ 只省 2.3%。
4. **alpha 确实无损，27 张全部 maxdiff = 0**（精一 15 + 皮肤 12）。`alpha_quality=100` 让 alpha 平面与 PNG 逐像素一致，透明边缘无白边/黑边。
5. **792 px 宽（手机 1×）全部通过**：精一 39.45–48.32 dB / SSIM ≥0.9983；皮肤 41.75–48.33 dB / SSIM ≥0.9965。**2376 px 宽（DPR3）是唯一的例外档**：精一落到 34.21–46.36 dB，其中 `_2` 组 5 张有 4 张 <38 dB。
6. **q95 不是逃生舱**：对 PSNR 最差的 2 张精一 + 1 张皮肤实测 q95，体积 **+30.6%~+31.8%**，PSNR 只 **+0.4~0.9 dB**（SSIM 倒是 +0.005）。这几张的误差是画风里的噪点/拼贴纹理，加码买不回来——**不值得为它们单独升档**。
7. **合并总计**（六目录、2032 张）：**1797.15 MiB → 338.78 MiB，省 1458.37 MiB（81.1%）**。其中**皮肤 + 精二两个目录就占全部节省的 89.7%**，其余四个目录合计只占 10.3%——这直接决定 §6 的落地顺序。

| 皮肤头像 | `public/assets/char/skin_avatar/*.png` | 288 | 17.19 MiB |

> ⚠️ **两处口径需要澄清（不影响结论，但影响归档命名）**
> 1. 任务描述里精一写作「含 `_1`/`_2`/无后缀」，**实测没有无后缀文件**：`illustration/` 下是 5 名角色 × 3 类 = 15 张，第三类是 **`_skin1`**（`char_4182_oblvns_skin1.png` 等）。
> 2. `illust/` 目录递归共 **511 项** = 233（精二 PNG）+ 277（`skin/` PNG）+ **1 个非 PNG**（已排除）。头像/半身像/皮肤头像三目录 100% 是 PNG，无混入。

### 1.2 转换参数

```python
im = Image.open(src).convert('RGBA')
im.save(dst, 'WEBP', quality=90, method=6, alpha_quality=100, exact=False)
```

`method=6`（最慢最小）、`alpha_quality=100`（alpha 位级无损）、`exact=False`（丢弃全透明像素底下的 RGB）。
**除 §4.3 的对照实验外，本文所有体积数字都是 `exact=False` 口径**（即最终建议口径）；E1 的数字是 `exact=True` 口径，故精二那行**偏保守**（见 §5 注）。

### 1.3 画质度量口径

两侧先按 alpha 合成到中性灰 `#808080`（透明像素底下的 RGB 无意义，直接比会得出假分数），再用 LANCZOS 重采样到目标宽度后比较。PSNR 在 RGB 上算；SSIM 在亮度通道算（11×11 高斯窗、σ=1.5、K1=0.01、K2=0.03、L=255，FFT 实现）。三个测量宽度：

- **全分辨率**：1:1 像素级，最严苛；
- **792 px 宽**：手机 CSS 逻辑像素铺满屏宽（1×）；
- **2376 px 宽**：同屏在 **DPR=3** 下的物理像素数（792 × 3）。

### 3.4 外推：277 张全转 q90 的总量

方法（对数分段映射，逐张计算，不用任何平均比）：

```
c_t = 各档 4 张字节的几何平均   = 345,221 / 3,630,970 / 8,132,982 B
r_t = 各档聚合压缩比 Σ原÷Σ新    = 3.35 / 6.32 / 5.19

对每个文件 v（共 277 个）：
    x = ln(v)
    r(v) = 在 (ln c_min, ln c_mid, ln c_max) 三点间对 r 线性插值；x 越界取端点值
    输出 += v / r(v)
```

| 参数口径 | 外推总量 | 节省 | 节省% |
|---|---|---|---|
| q90 `exact=False`（**建议口径**） | **158.94 MiB** | **727.11 MiB** | **82.1%** |
| q90 `exact=True`（对照） | 163.19 MiB | 722.85 MiB | 81.6% |

**对照：**把 12 张的总聚合比 5.27× 直接硬乘全量，得到 168.03 MiB——**比逐张插值多算 4.84 MiB（+3.0%）**。原因是抽样的体积权重和全量不一致：样本里 max 档占了 **67%** 的体积（全量里只占 26.6%），而 max 档的比只有 5.19×，被它一放大，平均比就被拉低了。**外推仍按分段走。**

**误差带**：只实测了 12/277 张（4.3%），外推值 158.94 MiB 的不确定度按 ±3% 估，**真实值预计落在 154–164 MiB**。落地后必须全量转一遍核对，不要拿外推值当验收值。

## 6. 落地建议

### 6.1 参数（定稿）

```python
im.save(dst, 'WEBP', quality=90, method=6, alpha_quality=100, exact=False)
```

- **q90**：DPR3 档 34–46 dB 的取舍点，q85 会再掉 ~1.3 dB、q80 会掉到 36.5 dB（E1 §7.2）。**不建议 q80。**
- **`alpha_quality=100`**：本次 27 张全部 alpha maxdiff = 0，**这一项不要动**。立绘的价值一半在轮廓，alpha 有损会立刻出现白边/毛刺。
- **`exact=False`**：全案再省 2.3%–48.1%（§4.3）。**默认开**；只有素材需要导回 PNG 二次编辑时才改回 `True`。

### 6.2 哪些目录**不值得**转 / 不值得**单独排期**

1. **`char/skin_avatar`（17.19 MiB，省 12.65 MiB）和 `char/avatar`（26.89 MiB，省 19.82 MiB）** —— 合计只占全案收益 **2.2%**，却涉及 **755 个文件**（37% 的文件数）。**建议排在最后，或者直接不做**：这点收益对整包体积没有感知，而收益真正在"列表页一次拉 50 个头像 2.9 MB → 0.77 MB"——如果当前头像列表没有分页/懒加载的痛感，**可以明确跳过，留待下一次打包**。
2. **精一 `_1` 组（5 张 / 2.63 MiB，省 2.21 MiB）** —— 占全案收益 **0.15%**。**不要为它单独开一轮**；但因为和 `_2`/`_skin1` 同目录同批，**顺手一起转**成本为零。
3. **`char/illust` 里 < 1 MB 的 83 张**（共 53.6 MiB；E1 实测最小 8 张聚合比仅 3.85×）—— 单张只省 0.3–0.4 MiB。不值得为它们调参数或做特殊处理。
4. **真正不该转的情形**：需要保留透明区 RGB 的源素材（美术返工、导出 PNG 交付）——`exact=False` 会永久丢弃那部分数据，且不可逆。**这类素材不要进转换管线**，或者单独走 `exact=True` 一份存档。

## 8. 风险

1. **DPR3 的 PSNR 回落（已知且真实）**：2376 px 宽下精一 `_2` 组 34.21–37.99 dB、皮肤 max 档 4 张里有 3 张低于 40 dB（最低 36.12 dB），均在 40 dB 的"不可辨"经验线之下。属于「细看能找到、正常观看不影响」。**如果目标机型是 DPR3 且立绘会全屏展示，这是唯一需要认真对待的场景**，也是不建议降到 q85/q80 的直接原因。
2. **Safari / iOS 完全未测**：本报告的 PSNR、SSIM、体积全部由 libwebp（Pillow 12.3.0）离线计算。**没有验证**：Safari 的 WebP alpha 解码结果、premultiplied alpha 在 Canvas/`<img>` 合成时与 PNG 的差异、iOS 上的解码内存峰值（2560² RGBA 单张 ≈ 26 MB）。上线前必须真机抽验，尤其是立绘页一次挂多张的场景。
